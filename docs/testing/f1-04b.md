# F1-04B — Falhas na captura estática GDI

## Base e implementação

Branch de trabalho `feature/f1-04b-gdi-failure-tests`, baseada no commit `e835776b034884cb505d5388524cf93b87a1fc6b` do PR #4. Na checagem inicial, os PRs #3 e #4 estavam abertos em rascunho. O [CI Windows do #3](https://github.com/Psykolic/eve-o-custom/actions/runs/42895701280) passou no commit `8b9789968da1ec107fd1643613621c744099be0d`. O [CI Windows por push da cabeça do #4](https://github.com/Psykolic/eve-o-custom/actions/runs/42928800789) também passou. Os logs registram 1.000 capturas e deltas zero em ambas as versões. A consulta de execuções disparadas por PR retornou vazia para o #4. O workflow anterior filtrava PRs destinados a `main`.

O diagnóstico Fase 1.3A usa a base do #4. A auditoria de arquitetura descreve a implementação anterior de captura estática e a ausência de testes no código que inspecionou. A base do #4 já contém o cleanup estruturado do #3 e o projeto `EveO.Tests`. Os valores estimados de CPU, memória, latência e limite de miniaturas DWM continuam pendentes de medição.

A API pública de captura estática delega a uma sobrecarga interna. O adaptador de produção faz as chamadas Win32 e `Image.FromHbitmap`. Os testes passam um adaptador por chamada e verificam a sequência e os argumentos. O diff de produção fica restrito à captura estática.

| Falha injetada | Tentativas esperadas |
|---|---|
| `GetDC` | Nenhuma, pois o DC de origem não foi adquirido |
| `GetClientRect`, `CreateCompatibleDC` | `ReleaseDC` |
| `CreateCompatibleBitmap` | `DeleteDC`, `ReleaseDC` |
| `SelectObject` inicial, com zero ou -1 | `DeleteDC`, `DeleteObject`, `ReleaseDC` |
| `BitBlt` | Restaurar bitmap anterior, `DeleteDC`, `DeleteObject`, `ReleaseDC` |
| Restauração com zero, -1 ou exceção | Tentar restaurar novamente, `DeleteDC`, `DeleteObject`, `ReleaseDC` |
| `Image.FromHbitmap` | Após restauração bem-sucedida, `DeleteDC`, `DeleteObject`, `ReleaseDC` |
| Exceção ou retorno de falha no cleanup | Continuar as tentativas aplicáveis na ordem esperada |

Os testes conferem as tentativas e a propagação de exceções simuladas. A garantia de liberação pelo Windows depende do resultado das operações nativas. Um bitmap ainda selecionado em um DC não pode ser excluído. [Microsoft Learn](https://learn.microsoft.com/windows/win32/api/wingdi/nf-wingdi-deleteobject)

## Evidência Windows local

Em 10/11/2026, com .NET SDK 8.0.428, o build Release passou com seis avisos, incluindo `NU1603` para `System.IO.Abstractions`. Passaram 23 testes, sendo 15 casos de falha GDI, sete testes de configuração e um stress WinForms. Na referência, o mesmo stress passou em uma cópia temporária com apenas `WindowManager.cs` do SHA `ea235957ddf55895792b3a1a2a68001ff8584722` e exclusão dos testes que dependem da sobrecarga nova.

| Implementação | Capturas medidas | GDI inicial → final | USER inicial → final |
|---|---:|---:|---:|
| Patch F1-04B | 1.000 | 23 → 23 | 25 → 25 |
| Referência `ea235957` | 1.000 | 23 → 23 | 24 → 24 |

Os quatro pontos de medição de cada execução foram 0, 100, 500 e 1.000. Ambos os deltas finais foram zero. O workflow usa o mesmo harness, exige a sequência completa nos dois CSVs e registra os SHAs e deltas no resumo. A comparação aceitou os dois CSVs locais e rejeitou um CSV de referência truncado em 500 capturas. Os CSVs e TRXs do runner ficam nos artefatos da execução.
